The concept I understand best now is that this assignment is a pipeline of separate stages: extract (sentiment_step and entities_step call the API and cache raw JSON), transform (sentences_table, opinions_table and entities_table flatten that JSON), and then combine (build_mentions and summarize_items turn the tables into counts). Keeping the stages separate meant I could debug a transform from cache/ or tests/fixtures without spending any of the 150 requests. The hardest transform was opinions_table. pd.json_normalize with record_path="sentences", meta=["review_id"] and record_prefix="sentence_" gave me one row per sentence, but each target only points to its assessments through a ref string, so I needed nested for loops and int(ref.split("/")[-1]) to find the matching item in that sentence's assessments list. I learned that json_normalize flattens one list well, but it cannot join rows by reference. I also saw why the stages need each other: opinion mining misses Pete, Tally and Otto because they have no assessments, so entity_mentions has to add them from entity recognition without duplicating mentions opinion mining already found. Next time I would build and check each stage one at a time instead of waiting for the final page to show a wrong count. I would also write the nested-loop version of opinions_table first on T3 (one sentence, two opposite opinions), because that case shows whether the ref lookup works.
