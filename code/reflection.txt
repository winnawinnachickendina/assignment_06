This assignment made the full review-analysis pipeline feel much more like a real data product than a toy exercise. The most important concept I learned is that the work is split into three distinct stages: extracting raw data from the API, transforming that JSON into tables, and then combining those tables into a single “what are people saying?” view. In practice, sentiment_step and entities_step call the REST API, save the raw answers to cache/, and only later do the transform functions flatten the nested JSON with pd.json_normalize, record_path, and meta. That separation matters because it keeps the slow, rate-limited API calls out of the logic that just reshapes the data. It also makes debugging easier, because I can inspect the cache files or the intermediate tables without burning another request.

The part I understood best was how the review pipeline turns sentence-level and entity-level signals into mention-level insights. Azure sentiment gives me sentence sentiment and opinion targets, while named-entity recognition catches people and products that opinion mining misses. The combine step is where the logic really clicks: build_mentions merges the opinion targets and entity mentions, then attaches the review and sentence context. This is why the final mentions table can represent things like “mocha latte,” “wifi,” and “Otto” even though each source alone is incomplete. I also learned why the subject classification step is important: each mention has to be categorized into product, atmosphere, customer service, or other, because otherwise the page cannot tell the owner what is actually being discussed.

The hardest part for me was the opinions_table transform. It was much deeper than a simple flattening job because each target points to its assessment through a ref string like “#/documents/0/sentences/1/assessments/0.” I had to parse the JSON in nested loops, use the relationType == "assessment" check, and match the target’s references back to the correct assessment text in that sentence. That was the moment I realized that json_normalize is great when the structure is a clean list of records, but it does not solve cross-references. The mention analysis then had to add entity mentions when opinion mining missed them, which showed how the two AI services complement each other instead of replacing each other.

I also became more careful with API details. The Azure sentiment and entity endpoints expect form data, while the decision model endpoint expects a JSON body. The question model also needs model and reasoning_effort passed as params, not as part of the request body. I learned to use raise_for_status() immediately so an HTTP 4xx or 5xx does not turn into a confusing later KeyError. The API key lives in .env, not in code, and caching matters because the portal is rate-limited. Saving the raw response to cache/ is not just a convenience; it is a way to avoid wasting the daily 150 requests and to make the transform steps reproducible.

One part I still want to explore more is the exact relationship between the mention-level subject classification and the QA box. I understand that question_scope builds a set of relevant items, locations, and subject filters from the user’s question, and that evidence_for narrows the mentions table to the rows that answer it. What I want to study next is how the LLM prompt is assembled in build_messages and why the briefing text is designed to give the model only counts and evidence instead of asking it to reason from raw reviews. I think that would help me understand prompt engineering more deeply, because the assignment shows that LLMs are best at summarizing and writing, while pandas is better at counting and filtering. My next step is to re-run the pipeline on the five test reviews and manually inspect one example like “Do people like the mocha latte?” to see exactly how the scope, evidence, and prompt all line up before I ask the model anything.
